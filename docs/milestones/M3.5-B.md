# M3.5-B — Debugging Foundation

Status: implementation on `m3.5b-debug-foundation`; awaiting code-level review before merge.

M3.5-B exists to make M3.5-C task/context-switch failures diagnosable before the scheduler exists.

It contains no task stacks, runnable queues, saved task context, scheduling policy, or context switching.

## Scope

M3.5-B adds four required pieces:

1. a fixed structured kernel event ring;
2. an allocation-free panic/fatal dump with frame-pointer backtrace;
3. repeatable host-side QEMU/GDB and symbolization tools;
4. a named self-test harness.

The interactive serial debug console remains deferred.

## Shared event IDs

`kernel/events.def` is the single source of truth for event IDs.

The file is deliberately simple enough to be consumed by both:

- the kernel at compile time through Rust `include!()`;
- host-side tools through a small parser.

Kernel and host tooling must not maintain independent handwritten event-number maps.

Initial events include:

- boot begin/complete;
- self-test begin/pass/fail;
- breakpoint;
- NMI;
- fatal exception;
- page fault;
- kernel panic;
- panic reentry;
- event-ring self-test.

## Structured event ring

The ring is a static fixed-capacity array of 256 slots.

Each record contains fixed-width numeric fields:

~~~text
tick
sequence
event_id
cpu
subsystem
level
flags
args[4]
~~~

No string is stored in ordinary event records.

### Publication

Writers obtain a monotonically increasing sequence number using an atomic fetch-add.

Before reusing a slot, the writer invalidates its previous incarnation by storing sequence `0` with Release ordering. A compiler fence keeps the payload overwrite after that invalidation. After the complete fixed record is written, a second compiler fence keeps the payload write before the final Release publication of the new sequence.

Readers use Acquire loads and accept a record only when the slot's published sequence matches the requested sequence before and after the record copy. Compiler fences keep the payload copy between those two checks. Sequence `0`, a mismatch, or a changed sequence makes the slot unavailable; readers do not retry or spin.

The record payload uses volatile access only so the copy is explicit and non-elidable. Synchronization comes from the atomic published sequence and compiler fences, not from volatile access.

This protocol is scoped to M3.5-B's bootstrap-CPU plus same-CPU asynchronous NMI/panic-dump model. It is not a general SMP sequence lock.

### Lock-free NMI path

Event writes:

- allocate no memory;
- acquire no spin lock;
- format no text.

The NMI handler records `NMI_RECEIVED` directly into the ring and uses the raw COM1 emergency path for its fixed human-visible line.

M3.5-B remains single-CPU. Before SMP event emission begins, FreeWorld must use per-CPU rings or another design that preserves the nonblocking NMI property and supplies the required cross-CPU synchronization.

## Serial is a renderer

The event ring is the structured log.

Serial output is a renderer/sink for that data, not the structured storage format itself.

`dump_recent_to_serial()` renders recent records during diagnostics using numeric event IDs. Host-side `tools/events.py` annotates those IDs from the same `kernel/events.def` table.

## Panic/fatal rule

Once panic/fatal diagnostics begin:

> No heap allocation, heap free, physical-frame allocation, or physical-frame return is permitted.

This is enforced mechanically:

- the heap allocator rejects alloc/free while the panic-active flag is set;
- the physical frame allocator rejects allocate/free while the same flag is set.

The panic path uses only fixed stack/static storage and existing mappings.

### Reentry

The first panic/fatal path atomically claims the panic-active state.

If diagnostics themselves panic or fault into another panic path, the reentrant entry:

1. does not format;
2. does not record another structured event;
3. writes one fixed message through raw COM1;
4. halts.

CI rejects any deliberate-panic boot containing:

~~~text
PANIC REENTRY
~~~

This makes accidental allocation or other recursive diagnostic failure visible.

## Panic text

Rust panic messages are the one bounded text exception to numeric kernel events.

M3.5-B captures the panic message into a fixed 256-byte buffer.

If the message exceeds the buffer, it is truncated and marked as truncated.

No allocation is performed while capturing it.

The structured `KERNEL_PANIC` event stores numeric metadata including message length/truncation state. The fixed message buffer remains separate from ordinary event records.

## Backtrace

Frame pointers are forced for the entire `x86_64-unknown-none` target in `.cargo/config.toml`, not only for a debug profile:

~~~text
-C force-frame-pointers=yes
~~~

The initial backtrace implementation is intentionally bounded and best-effort:

- maximum 32 frames;
- no allocation;
- follows the RBP chain;
- requires aligned canonical addresses;
- refuses backwards/non-increasing chains;
- refuses frames beyond a conservative 1 MiB window from the current stack pointer;
- emits return addresses only when they fall inside the runtime kernel image range reported by `BootInfo`.

A panic/fatal serial dump emits:

~~~text
FreeWorldOS: BACKTRACE begin frames=N
FreeWorldOS: BT[00]=0x...
...
FreeWorldOS: BACKTRACE end
~~~

The host symbolizer consumes these lines.

This is diagnostic infrastructure, not a claim that corrupted stacks can always be unwound safely.

## Fatal exceptions

Fatal CPU exceptions use the same panic-active, no-allocation dump path.

The fatal record carries numeric context such as:

- faulting instruction pointer;
- interrupted stack pointer;
- exception error code;
- fault address where applicable.

Page faults emit the dedicated `PAGE_FAULT` event.

The ordinary breakpoint self-test remains nonfatal and records `BREAKPOINT`.

## Raw serial emergency path

`arch::serial::write_raw()` writes bytes directly to COM1 without:

- `fmt`;
- allocation;
- locks.

It exists for:

- NMI fixed messages;
- panic reentry.

Normal diagnostics continue using the regular serial formatter where safe.

## Named self-test harness

Per-milestone tests now run through one harness.

Each test emits:

~~~text
FreeWorldOS: SELFTEST BEGIN name=<name>
FreeWorldOS: SELFTEST PASS name=<name>
~~~

or a named FAIL before entering the panic path.

Current names include:

- `m1.memory`;
- `m1.exception.breakpoint`;
- `m3.heap`;
- `m3.5a.frame_reuse`;
- `m3.object`;
- `m3.5b.event_ring`.

The harness also records structured `SELFTEST_BEGIN`, `SELFTEST_PASS`, and `SELFTEST_FAIL` events using a stable FNV-1a hash of the static test name as a compact correlation value.

Existing milestone-specific proof lines remain during this transition so historical CI evidence stays readable.

## Event-ring CI test

The M3.5-B ring self-test writes a `DEBUG_RING_SELFTEST` record with known numeric arguments and reads that exact sequence back.

The test fails if:

- the sequence cannot be read;
- the event ID changes;
- either known argument changes.

CI also requires the rendered `0x0300` event to appear in the cumulative self-test serial log.

## Deliberate panic CI boot

M3.5-B adds a separate panic-test kernel image.

It deliberately executes:

~~~text
panic!("M3.5-B deliberate panic test")
~~~

CI requires:

- `KERNEL PANIC`;
- the exact fixed panic message;
- a nonempty backtrace;
- at least one `BT[NN]` address;
- recent event-ring output;
- the `KERNEL_PANIC` event;
- the pre-panic debug event;
- no `PANIC REENTRY`.

The panic image is separate so the normal cumulative boot can still reach bootstrap completion.

## Deliberate fatal-exception CI boot

A second dedicated diagnostic image deliberately reads an unmapped canonical address and must enter the page-fault path.

CI requires:

- `FreeWorldOS: FATAL`;
- `#PF page fault`;
- the expected fault address;
- a nonempty frame-pointer backtrace;
- a structured `PAGE_FAULT` event;
- the pre-fault debug event;
- no `PANIC REENTRY`.

This separately proves that fatal CPU exceptions use the same fixed, nonallocating diagnostic foundation as Rust panics.

## Host tools

M3.5-B establishes `tools/` as the common host-debugging location.

### `tools/qemu-gdb.sh`

- builds the current image;
- locates the BIOS image and kernel ELF;
- boots QEMU paused with its GDB server;
- connects `gdb-multiarch` or `gdb`;
- records serial output to a known log.

The kernel is relocatable, so runtime symbol relocation remains explicit.

### `tools/symbolize-backtrace.py`

- reads `BT[NN]` lines;
- reads the boot log's `virt_base`;
- rebases runtime addresses;
- invokes `llvm-addr2line` or `addr2line`.

### `tools/events.py`

- parses `kernel/events.def`;
- validates uniqueness;
- decodes one event ID;
- annotates serial EVENT lines.

CI syntax-checks these host tools and validates the shared event table.

## Deferred work

M3.5-B does not add:

- interactive kernel debug commands;
- remote debugger protocol inside the kernel;
- scheduler tracing;
- per-CPU event rings;
- durable event storage;
- user-mode access to the ring;
- task objects or task stacks.

Those land only when the relevant substrate exists.

## M3.5-C gate

M3.5-C may begin only after M3.5-B is approved and merged.

M3.5-C then adds:

- task objects;
- kernel-owned task stacks backed by the M3.5-A recycler;
- guard pages;
- saved register context;
- runnable state;
- deterministic scheduler/context switching.

The debugging foundation remains usable while that work is brought up.
