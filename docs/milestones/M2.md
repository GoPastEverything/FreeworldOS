# M2 — Interrupt Controller and Measurable Timer

Status: implementation complete on `m2-apic-timer`; awaiting/under final merge validation.

M2 establishes a deterministic interrupt-controller baseline, a measured local timer, proven interrupt delivery, and an architecture-neutral runtime time hook.

## Landed so far

### Exception-stack hardening

- dedicated 20 KiB IST stack for double fault;
- dedicated 20 KiB IST stack for NMI;
- dedicated 20 KiB IST stack for machine check;
- NMI handler is intentionally tiny and non-faulting.

The NMI handler must never allocate, lock, map pages, or call code that can fault. If serial output later gains a lock, NMI output must use a lock-free/direct path.

Guard pages are deferred until FreeWorld allocates kernel stacks itself, around M3.

### Legacy PIC quarantine

The 8259 PIC pair is:

1. fully masked before reprogramming;
2. remapped to vectors `0x20` / `0x28`;
3. configured with the standard master/slave cascade;
4. fully masked again;
5. read back to verify both masks are `0xff`.

Vectors `0x20..0x2f` have defensive handlers so an unexpected legacy PIC vector does not fall into an unhandled IDT entry.

### Local APIC baseline

The xAPIC path:

- verifies APIC support with CPUID;
- preserves the firmware-selected APIC physical base;
- refuses to silently switch an already-active x2APIC back to xAPIC;
- installs spurious vector `0xff`;
- installs timer vector `0xe0`;
- explicitly masks local APIC sources not yet owned by FreeWorld;
- configures LINT1 as NMI;
- leaves the timer masked and stopped until measured.

`sti` is enabled only in the final M2 delivery proof after the PIC is masked, LAPIC state is deterministic, calibration has completed, and the periodic timer is programmed.

### Device-memory mapping

The LAPIC is no longer accessed through the bootloader's general physical-memory direct map.

FreeWorld now has an architecture-neutral memory cache policy:

- `MemoryCachePolicy::Normal`
- `MemoryCachePolicy::Device`

On x86_64, Device mappings use the PWT+PCD encoding only after FreeWorld verifies:

- CPUID reports PAT support;
- IA32_PAT entry 3 is strong-uncacheable.

The LAPIC's 4 KiB frame is mapped at a dedicated supervisor-only, NX FreeWorld kernel virtual address with Device caching.

If the bootloader direct map also covers the LAPIC physical range, FreeWorld first translates that alias to determine its actual leaf size. A 4 KiB or 2 MiB leaf is updated in place to the same uncached type while preserving its existing flags; a 1 GiB leaf is rejected. This avoids silently leaving a cacheable alias or creating conflicting cache types for the same MMIO registers.

### Timer calibration

The local APIC timer is calibrated with interrupts disabled against PIT channel 2.

Calibration procedure:

1. PIT channel 2 is programmed as a polled mode-0 one-shot.
2. The PC speaker remains disconnected.
3. The APIC timer is kept masked and configured divide-by-16.
4. The APIC initial count is set to `u32::MAX`.
5. PIT channel 2 gates a window of 11,932 PIT clocks (~10 ms).
6. The APIC current count is sampled after PIT terminal count.
7. Five samples are collected.
8. The median measured counter rate is retained.

Calibration rejects:

- PIT arm/terminal-count timeout;
- an APIC timer that reaches zero during the window;
- zero-tick samples;
- arithmetic overflow;
- an extremely broad implausible rate.

CI does **not** assert a tight timing threshold. It requires only a successful nonzero calibration marker; the broad plausibility guard lives in the kernel.

Example QEMU BIOS result:

~~~text
apic: timer calibration pit_hz=1193182 window_count=11932
samples=[621857, 624983, 624981, 624952, 624919]
median_hz=62494257
source_hz_est=999908112
~~~

These are virtual-machine measurements, not real-hardware timing claims.

## Known limits

### x2APIC

M2 currently implements only the MMIO xAPIC backend.

If firmware has already enabled x2APIC, FreeWorld returns `X2ApicAlreadyActive` rather than silently changing APIC mode. Modern UEFI systems may arrive in x2APIC mode, so x2APIC is a known compatibility limit until a separate backend is implemented.

### UEFI

The build produces UEFI media, but CI still boot-tests BIOS only. Neither LAPIC mapping nor calibration is claimed as UEFI-hardware proof yet.

### Legacy PIC spurious IRQ15

The defensive PIC handlers still need IRQ15-specific acknowledgement behavior before legacy PIC delivery is ever relied upon: a spurious IRQ15 requires an EOI to the master PIC cascade line, while the slave must not receive an EOI for the spurious request. The PIC remains fully masked in M2, so this is recorded rather than treated as timer-delivery infrastructure.

### SMP and LINT1

M2 is bootstrap-CPU-only. LINT1 is configured as NMI on the bootstrap processor. When SMP arrives, FreeWorld must assign local interrupt ownership deliberately instead of cloning that firmware-facing LINT1 policy to every application processor.

The SMP bring-up list also includes cross-CPU TLB shootdown with acknowledgement before a physical frame can be returned for reuse. M3.5-A's local `unmap_page()` invalidation is sufficient only while one CPU owns execution.

### Physical direct map

M2 hardens the direct-map alias that contains LAPIC MMIO when present. The broader M1 bootloader physical-memory mapping is still a temporary bootstrap mechanism and must be hardened or replaced before untrusted userspace, no later than M5.

## Interrupt-delivery proof

The calibrated APIC counter is now used to program a 100 Hz periodic test interval.

The first intentional `sti` in FreeWorldOS occurs only after:

- the 8259 PIC pair is fully masked;
- LAPIC state is deterministic;
- the timer vector is installed;
- the timer frequency is calibrated;
- the periodic initial count is derived from the measured divided counter rate.

The timer interrupt path performs only:

1. an atomic tick increment;
2. LAPIC EOI.

It does not allocate, acquire locks, write serial output, map memory, or invoke scheduler policy.

Bootstrap proof enables IF, executes `hlt` until at least three periodic timer interrupts have arrived, then logs the observed nonzero tick count. CI checks only that delivery occurred; it does not enforce elapsed-time or jitter thresholds.

Scheduler policy and real-time/jitter claims remain outside this proof.


## Architecture-neutral runtime time hook

Generic runtime code does not call APIC functions directly.

`rt::time` exposes:

- `now() -> Tick`
- `tick_period() -> Option<TickPeriod>`

The target-specific `arch` layer supplies only the abstract tick count and tick-period hooks. On x86_64 those are backed by the calibrated LAPIC timer, but callers outside `arch/` do not depend on APIC types or registers.

The previous M0 scheduler-local fake tick counter and premature task/scheduler scaffolding were removed. A real scheduler needs stack allocation, task ownership, saved register state, and object/capability lifetime rules, so it is intentionally deferred until after M3.

## Panic discipline

Once M2 enables maskable interrupts, the panic handler disables interrupts before printing the panic and entering the halt loop. This prevents the periodic APIC timer, and future interrupt sources, from continuing to execute code after a kernel panic.

Fatal CPU exception paths already enter with maskable interrupts disabled by the processor/interrupt-gate path and remain terminal.

## Milestone boundary

M2 ends with:

- legacy PIC quarantined;
- xAPIC brought to deterministic state;
- LAPIC MMIO mapped through FreeWorld's device-memory policy;
- APIC timer calibrated against PIT channel 2;
- periodic 100 Hz delivery proven after the first intentional `sti`;
- atomic tick count and EOI-only timer interrupt path;
- architecture-neutral `rt::time` tick/period interface;
- panic path disabling interrupts.

M2 does **not** include task scheduling, context switching, jitter guarantees, or a high-resolution clock.

Planned ordering:

- **M3:** heap + FW objects/handles + capability skeleton;
- **M3.5:** task stacks, saved context, deterministic scheduler/context switching;
- later: high-resolution monotonic time using an invariant TSC or another validated clock source when a consumer requires sub-tick precision.

The existing M4+ milestone numbering remains unchanged, preserving the already-frozen userspace/callgate sequence.
