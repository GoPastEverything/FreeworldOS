# M3 — Heap, Native Object, Handles, and Rights

Status: implementation complete on `m3-heap-objects`; awaiting code-level review before merge.

M3 provides the minimum ownership substrate required before task stacks or context switching can exist.

## Scope lock

M3 contains exactly:

1. a kernel heap;
2. one live FreeWorld-native object type;
3. a handle table;
4. per-handle rights enforcement;
5. handle close that actually releases the object and returns its heap allocation for reuse.

M3 does **not** contain:

- task stacks;
- saved CPU context;
- runnable queues;
- scheduling policy;
- context switching;
- physical-frame reclamation.

Those remain outside M3. Scheduler/context work is M3.5 and begins only after this ownership model is review-approved.

## Kernel heap

The M3 heap reserves a fixed 512 KiB kernel virtual range:

~~~text
base:       0xffff900000000000
pages:      128
page size:  4096 bytes
heap size:  512 KiB
block size: 16 bytes
~~~

Each heap page receives a unique physical frame from the existing M1 monotonic frame allocator and is mapped supervisor RW + NX.

### Physical-frame rule

The heap never calls `unmap_page()` to reclaim backing frames.

The 128 backing frames, plus any page-table frames required to establish the heap mapping, are one-way bootstrap allocations. M3 does not add a physical-frame free path and does not pretend that `unmap_page()` recycles frames.

Only allocations *inside the permanently mapped heap* are recycled.

### Allocation model

The heap uses a fixed bitmap with 16-byte allocation units.

Properties:

- no allocator metadata allocations;
- arbitrary Rust `Layout` alignment is respected;
- allocations are serialized by the heap lock;
- deallocation returns bitmap blocks for reuse;
- live allocation/requested-byte counters are maintained for proof;
- current interrupt handlers remain allocation-free, so the M3 single-core lock cannot be recursively entered from timer interrupt context.

The allocator lock is not an SMP design. It is sufficient for the current single-core milestone and must be revisited before interrupt handlers or multiple CPUs are allowed to allocate.

## First native object

M3 introduces one live native object type:

~~~text
CounterObject
~~~

A counter owns:

- a FreeWorld object ID;
- one atomic `u64` value.

The object is allocated through `Arc<FwObject>`. This separates object lifetime from the handle-table slot and gives later handle duplication/shared-object work a compatible ownership foundation without implementing duplication in M3.

No process, module, task, file, or scheduler object is made live in this milestone.

## Handle table

M3 uses a fixed 64-slot handle table.

A handle encodes:

- slot index;
- slot generation.

Handle value zero is invalid.

When a handle closes:

1. the entry is removed from the slot;
2. the generation advances;
3. the table lock is released;
4. the removed `Arc` is dropped outside the table lock.

This makes the closed handle stale immediately and prevents an old numeric handle from addressing a new object placed in the same slot.

## Rights

Rights belong to the handle entry, not the object.

M3 defines:

- `READ`
- `WRITE`

Counter operations request rights at handle lookup:

- counter read requires `READ`;
- counter increment requires `WRITE`.

A handle lacking the requested rights returns `AccessDenied` before the object reference is handed to the operation.

This is the first FreeWorld capability check. M3 does not yet implement transfer, duplication, inheritance, process-local tables, or policy.

## Close and reclamation proof

M3's close proof is deliberately stronger than checking one destructor call.

The CI self-test:

1. records initial heap accounting and live object count;
2. creates a READ-only counter;
3. proves READ succeeds;
4. proves WRITE is denied;
5. closes the handle;
6. proves the stale handle is rejected;
7. proves object count and heap accounting return to baseline;
8. creates a READ+WRITE counter and proves both operations;
9. closes it;
10. creates, reads, and closes 24,000 additional counters sequentially;
11. proves final live object count is zero;
12. proves final live heap allocation count is zero.

The sequential reuse loop represents more aggregate object allocation than the 512 KiB heap could retain if closed objects leaked. Passing it therefore proves that handle close reaches object destruction and heap-block reuse.

It does **not** prove physical-frame reuse. Physical frames remain intentionally monotonic.

## CI proof

The self-test image requires:

~~~text
FreeWorldOS: M3 heap self-test: passed
FreeWorldOS: M3 object self-test: passed reuse_iterations=24000 live_objects=0 live_heap_allocations=0
~~~

The existing M0-M2 proofs remain required in the same boot.

## M3.5 gate

M3.5 may begin only after M3 is merged with this invariant intact:

> Closing the final handle to a native object releases that object and returns its heap storage for reuse without claiming physical-frame reclamation.

M3.5 can then add:

- task objects;
- kernel-owned task stacks;
- guard pages;
- saved register context;
- runnable state;
- deterministic scheduler/context switching.

Those concepts are intentionally absent from M3.
