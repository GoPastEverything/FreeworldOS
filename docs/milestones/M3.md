# M3 — Heap, Native Object, Handles, and Rights

Status: merged and frozen on `main` at M3.

M3 provides the minimum ownership and allocation substrate required before task stacks or context switching can exist.

## Scope lock

M3 contains:

1. a deterministic kernel heap;
2. one live FreeWorld-native object type;
3. a generational handle table;
4. per-handle rights enforcement;
5. rights-reducing handle duplication;
6. handle close that releases the object on the last reference and returns heap storage for reuse;
7. an interrupt-context guard that forbids heap allocation/free from handlers in debug builds.

M3 does **not** contain:

- task stacks;
- saved CPU context;
- runnable queues;
- scheduling policy;
- context switching;
- physical-frame reclamation.

Those remain outside M3.

## Kernel heap

The M3 heap reserves a fixed 512 KiB kernel virtual range:

~~~text
base:       0xffff900000000000
pages:      128
page size:  4096 bytes
heap size:  512 KiB
~~~

Each heap page receives a unique physical frame from the existing M1 monotonic frame allocator and is mapped supervisor RW + NX.

### Physical-frame rule

The heap never calls `unmap_page()` to reclaim its backing frames.

The 128 backing frames, plus page-table frames required to establish the heap mapping, remain one-way bootstrap allocations. M3 does not add a physical-frame free path and does not claim that `unmap_page()` recycles frames.

Only allocations inside the permanently mapped heap are reclaimed.

### Deterministic allocation structure

The heap is split into two fixed halves.

The first 64 pages are size-class pools:

~~~text
32, 64, 128, 256, 512, 1024, 2048 bytes
~~~

Each class uses an intrusive free list. Allocation and free are constant-time once the class is selected; there is no first-fit scan through fragmented heap space.

The remaining 64 pages form a page-granularity buddy pool for allocations larger than 2048 bytes or requiring larger alignment.

The page buddy has seven orders covering 1 through 64 pages. Allocation/free takes at most six split/merge steps, so its runtime is bounded by the fixed heap geometry rather than fragmentation history.

### Bad-free discipline

A heap free is a kernel correctness boundary.

The allocator panics before accounting changes if any of these occur:

- null free;
- pointer outside the expected pool/class;
- pointer not aligned to its class/order;
- free with a layout that does not match the recorded large allocation;
- freeing an unallocated small block;
- double free;
- freeing an interior page of a large allocation.

Live allocation counters are decremented only after a valid deallocation completes. Accounting cannot silently hide a bad free.

### Interrupt-context allocation guard

FreeWorld tracks interrupt-handler nesting depth in the architecture layer.

Every x86_64 interrupt/exception handler enters the depth scope on entry. Returning handlers leave it on exit.

In debug builds, the global allocator asserts that allocation and deallocation occur only at interrupt depth zero. This turns a future attempt to allocate while normal code holds the heap lock into an immediate kernel failure instead of a silent single-CPU deadlock.

Current timer and other interrupt paths remain allocation-free.

The heap lock is still a single-core M3 mechanism, not the final SMP allocator synchronization design.

## First native object

M3 introduces one live native object type:

~~~text
CounterObject
~~~

A counter owns:

- a FreeWorld object ID;
- one atomic `u64` value.

Objects live behind `Arc<FwObject>`, so object lifetime is independent of any single handle-table slot.

No task, file, process, module, scheduler, or VFS object becomes live in M3.

## Handle table

M3 uses a fixed 64-slot table.

A handle encodes:

- slot index;
- 32-bit slot generation.

Handle value zero is invalid.

### Close

When a handle closes:

1. the entry is removed;
2. the generation advances;
3. the table lock is released;
4. the removed `Arc` is dropped outside the table lock.

Dropping outside the table lock prevents object destruction or heap deallocation from running under the handle-table lock.

### Generation exhaustion

A slot does not wrap its generation from `u32::MAX` back to 1.

When a close consumes generation `u32::MAX`, that slot is retired permanently. This sacrifices one table slot after 2^32 lifetimes rather than allowing an ancient handle value to become valid again.

## Rights and capability monotonicity

Rights belong to the handle, not to the object.

M3 defines:

- `READ`
- `WRITE`

Counter read requires `READ`; increment requires `WRITE`.

A handle lacking the requested rights gets `AccessDenied` before an object reference is returned.

### Duplicate

`duplicate(source, new_rights)` creates a second handle to the same object only when:

~~~text
new_rights ⊆ source_rights
~~~

Rights may stay equal or shrink. They can never grow.

The duplicate owns another `Arc` reference to the same `FwObject`.

If the table is full, both normal insertion and duplicate return the rejected `Arc` out of the locked table operation and drop it only after the table lock is released.

## CI ownership/capability proof

The M3 self-test proves:

1. READ works on a READ handle;
2. WRITE through that handle is denied;
3. a closed handle becomes stale;
4. slot reuse does not revive the stale generation;
5. duplicating READ|WRITE to READ succeeds;
6. the reduced duplicate cannot WRITE;
7. asking the READ duplicate to mint READ|WRITE fails;
8. closing one of two handles leaves the shared object alive;
9. closing the final handle destroys the object and returns its heap storage;
10. a full-table insertion fails without leaking the rejected object;
11. 24,000 sequential create/read/close cycles complete;
12. final live object count is zero;
13. final live heap allocation count is zero.

The self-test image requires:

~~~text
FreeWorldOS: M3 heap self-test: passed
FreeWorldOS: M3 object self-test: passed reuse_iterations=24000 duplicate_subset=ok shared_lifetime=ok table_full_drop=ok live_objects=0 live_heap_allocations=0
~~~

The existing M0-M2 proofs remain required in the same boot.

## M3.5 gate

M3.5 may begin only after M3 is merged with these invariants intact:

> Rights on duplicated handles can only stay equal or shrink.

> Closing one handle does not destroy an object while another handle still references it.

> Closing the final handle destroys the object and returns its heap storage for reuse.

> Heap reclamation does not imply physical-frame reclamation.

### First M3.5 prerequisite: physical-frame reuse

M3.5 needs task stacks whose physical backing can eventually be returned when tasks terminate.

Therefore the **first** M3.5 memory change is M3.5-A: a physical-frame free stack/recycler layered behind the existing frame-allocation interface. Task stacks, guard pages, saved context, and scheduler work do not start until frame return is real and tested. See `M3.5-A.md`.

After that prerequisite, M3.5 can add:

- task objects;
- kernel-owned task stacks;
- guard pages;
- saved register context;
- runnable state;
- deterministic scheduler/context switching.
